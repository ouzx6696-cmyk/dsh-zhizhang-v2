# 织章 V2 深度评估与优化计划

2026 年 11 月 19 日 · 评估对象为当前 V2 工作树与已交付的 2.0.0 安装包。适配宿主为 DsH Web 0.2.2-rc.4。

## 产品判断

织章有两个关键使用场景。写番茄连载时，作者需要知道某个人物在某一章、某一段已经知道什么，并能用这个边界约束候选正文。写头条时，作者需要从六种体裁与内容线组合中选定一种，修订、质检、验收，并把自己批准的那个版本交出去。两条线共有的产品承诺是作者能分清自己正在编辑的文字、模型建议的文字和已经批准的文字。

两条主流程、SQLite 事务、版本批准、候选隔离与本地 Markdown 交稿均已接通。**当前最紧要的产品问题发生在日常写作中。作者点保存后继续输入可能丢字，同一条设定在两个入口可能有不同答案，合规篇幅的头条长稿可能在调用模型前就耗尽默认预算。** 建议先发修复版，再扩展工作台。每一阶段以作者能完成的任务验收。

## 分阶段实施

下列为一个熟悉项目的工程师在当前环境有连续工作时间时的估算。阶段可单独交付。P0 优先于性能目标与新增页面。

### 第一批 · 能重建版本，作者的文字和决定一致 · 3–5 个工程日

1. **留存可构建的源码基线。** 核对当前修改和新增文件，将交付源码、锁文件、构建命令、目标宿主和产物摘要关联到同一提交。在全新目录按锁文件安装、检查、构建、打包，在隔离宿主打开两个入口。留存当前 2.0.0 安装包用于比较。
2. **修复编辑器保存协议。** 先固定慢响应复现，再覆盖本地草稿基准、浏览器存储写失败提示及双标签冲突。允许作者保留冲突中的本地副本并对照服务器版本。审稿、验收、采纳和定稿时，界面要清楚标明实际作用的已保存修订；有未保存文本时给出明确处理路径。
3. **修正设定与用量的一致性。** 用已批准事件重建现有设定的决定顺序，校验直接查询、回放和冻结输入。将迟到结算与事件写入关联。对历史重复记录先做只读核对，仅对可判定的重复生成修正记录；旧库缺少调用标识时保留待核对状态。
4. **收口任务入口。** 统一锁稿、已有活跃任务、重试条件和并发判断。修复版的验收样本包含空库、含旧任务的 2.0.0 库、两标签页和一次重启。

**退出条件**　慢响应场景零丢字；同一事实三个入口一致；两份用量账一致；从洁净检出能重建并安装修复包。涉及数据变更，先在副本迁移并核对修订、事件、批准和候选数，记录还原步骤。

### 第二批 · 两条写作流程都能纠错和恢复 · 5–8 个工程日

| 工作项 | 交付内容与验收 |
| --- | --- |
| 模型调用与恢复 | 区分“已建任务、尚未发送”和“提供方已接收”；保留调用标识、提供方、模型、阶段、四类可得用量及失败原因。当前执行中任务保存在进程 Map，启动补偿主要覆盖交稿，失败路径会把缺少的结算量归为零。模拟发送前重启、流中断、缺用量、取消和插件卸载，恢复后能解释现状，待核对用量不会触发静默重发 |
| 中文预算与生成质量 | 接通前置估算与失败说明。保留同一任务跨重试的两轮自动回改上限。离线使用宿主流回放覆盖格式错误、截断、迟到和缺用量；在有提供方凭证和已定费用上限的环境，用合成长短稿核对真实响应与结算。番茄额外检查人物提前知情，头条额外检查事实依据及硬门 |
| 番茄作者体验 | 在编辑区支持查看当前位置的人物所知、设定来源、锁定和生效区间。把已有证据记录、候选对照与该段正文连起来。验收用两章、两人、不同知情时点，同一任务冻结后再改设定，旧候选仍显示其原依据 |
| 头条作者体验 | 接通原稿改题和应用标题候选，展示当前版本最近一次 QA、未通过项、验收退回原因和下一步。交稿页区分“已批准、已记录、文件已写入、需处理文件冲突”。有标题的两种体裁与微头条各走一次恢复路径，重新打开仍可核对结果 |
| 备份与恢复 | 复用已有清单和哈希校验。先交付停写状态下的整库备份与恢复流程，校验清单包含预期数据库，对 `work.db` 与宿主 `workspace.sqlite` 的命名做显式映射，纳入交稿文件或校验其可重建性。先恢复至新目录，再在隔离宿主验证正文、设定、候选、批准和导出文件。保留原库供切回 |

**退出条件**　作者可在当前稿解决超长标题；正常中文长稿在发送前能知道预算够不够；重启和缺用量有可见处理路径；旧版本备份可在一个全新 profile 恢复。付费模型质量单列报告，记录样本和提供方版本。

### 第三批 · 让长期使用的项目保持流畅 · 3–5 个工程日

| 本机合成基线 | 当前值 | 实施顺序与建议指标 |
| --- | --- | --- |
| 650 章，每章 1 万个汉字，无长任务历史 | 打开一章时序列化快照 71,361 字节，中位 1.18 ms；热导航读取中位 0.73 ms | 保留目录只取元数据及增量回放。相同夹具下保持首次快照低于 100 KiB |
| 同一章 1 万字，已有一条取消任务，再新增 100 条各含 1 万字候选的已舍弃任务 | 快照从 61,710 增至 6,108,511 字节；读取与 JSON 序列化中位从 0.35 增至 50.34 ms | 优先拆任务摘要和详情。首页只取当前工作所需的候选与任务，历史按游标读取，展开时取冻结输入及候选全文。相同夹具首次响应目标低于 150 KiB，历史仍可逐条取回 |
| 6,000 章、6,000 个关系的领域重排影响计算 | 中位 2.12 ms。应用层提交前还逐项扫描原数组检查成员 | 测量完整预览与确认链路，再用集合校验成员并复用章序索引。验收完整链路的耗时和结果等价性 |
| 浏览器写作与长目录 | 每次输入同步写入整篇本地草稿；每次完整渲染重建目录。大量设定随活动稿一起加载 | 首先测按键到绘制、切稿到可编辑、设定数量与 DOM 节点。草稿写入合并时保留切稿与失焦落盘路径，并验证意外关闭。优先分区更新和设定分页；实测节点开销占主导时引入目录窗口化 |

**量测口径**　以上毫秒为内存 SQLite 和本机 Node 的中位数。后续固定运行环境和夹具，分别记录冷/热、磁盘 SQLite、主线程、响应字节及 Chromium 端到端 p50/p95。建议以 650 章基线上的切稿到可编辑 p95 ≤ 200 ms、连续输入到下一帧 p95 ≤ 50 ms 为首轮目标；首次采样后复核设备差异。普通 CI 保留稳定的字节数和查询范围断言，波动较大的延迟放在定机基准。模型首字延迟单独量测。

### 第四批 · 降低后续维护和发版成本 · 2–4 个工程日

- **缩小跨层改动。** 当前 `src/host/workspace.ts` 的 719 行同时包含建表、SQL、两条产品线操作、运行结算和快照拼装。跟随前三批修复，先把变动过的设定选择、运行结算和快照查询归到清晰的领域或存储接口。延续现有事务边界，逐个操作比较旧库结果，避免整层同时替换。
- **让类型检查覆盖发货入口。** 当前 TS 检查包含 `src/**/*.ts`，宿主插件、模型桥和作者页面是 JS/MJS。先为这三处补请求、返回和错误的边界校验或类型检查。浏览器以可执行的验收覆盖保存、采纳和交稿的实际行为。
- **保持测试简单。** 日常保留一个 `npm run verify`，发版保留一个全量入口，历史规则按需取证。优先扩充现有跨层断言，例如取消后同时查表和读模型。浏览器只维护“编辑过程中保存、番茄设定到定稿、头条改题到交稿”三条旅程，共用合成数据。宿主单独验证安装、所有者权限、卸载和恢复；模型故障用确定性传输代替外网调用。
- **增加本地可诊断性。** 界面按原因提示可采取的动作，技术诊断只保存操作、版本、阶段、时间、错误码、关联号与必要计数。正文、完整提示词和凭证留在其既有受控位置。验证常见失败可凭诊断号解释，作者可明确看到导出能否重试。
- **整理发布入口。** README 首页保留安装、当前支持版本、验证命令与故障恢复；历史取证保留独立入口。把可重复的浏览器和性能夹具从临时环境纳入仓库；生成安装包时核验入口、资源、版本、摘要及隔离宿主冒烟结果。
- **核对长时间写作的可用性。** 用键盘、中文输入法组词、窄屏和深色主题各走保存与冲突恢复；轮询更新后检查焦点、光标和滚动位置。请番茄与头条作者分别从空项目完成第一份定稿或交稿，记录卡住的具体步骤，据此决定是否优先做章节查找、继续上次编辑或更细的逐段差异视图。

**退出条件**　新检出能按文档重建，离线主流程可用一条命令定位失败，安装包可追到源码；宿主升级时能单独验证适配层，作者正文无需进入诊断日志。

## 发布顺序与成效判断

建议先用第一批交付 2.0.x 修复版。第二批中改题、生成恢复、备份可各自交付，涉及库结构的改动先保留兼容读取并验证旧库副本。第三批的快照拆分可在修复版发出后提前启动，与写作功能共享同一查询契约。第四批的源码归属、回归和类型检查随相关改动完成，最后集中做洁净安装和恢复演练。四批合计约 **13–22 个工程日**，实际排期以旧库修复和宿主复验结果调整。

发版首先看丢字复现数、相同事实的读取分歧、重复结算三项是否归零。试用阶段再统计完成两条作者旅程的成功率、作者找回旧版本所需时间、生成失败原因、任务历史带来的响应增长。样本量与失败原因一同报告。候选采纳率可作体验信号，涉及题材和作者个人风格，应结合作者弃用原因解读。

标题 34 字符、QA 84 分、两次审稿打回、两轮自动回改、固定交稿末句及两条线的状态语义都列入发版回归。多人协作、新宿主和外部发布集成待出现真实使用需求后再定优先级。
